# Multi-tenancy

One institution is one tenant. A global user may hold independent active memberships in multiple institutions. The browser's selected institution ID is never proof of access.

Implemented request path: validate session → validate UUID selector → resolve active institution, membership and role → require an explicit operation permission and, for module endpoints, the enabled institution module → scoped query/transaction that revalidates access. Listings join only the current user's active memberships in active institutions. No tenant grant is cached in sessions. Unassigned roles deny workspace access. Admin and Principal manage existing institution memberships; reads/writes lock the institution before membership rows, recheck the actor and protect the last active Admin. Frozen/inactive institutions deny tenant operations while preserving records and global identity sessions.

Persistence has explicit institution ownership on memberships, composite membership PK and foreign keys. Admission candidates, academic offerings, students/enrollments, collections and reminder rows now carry institution ownership and composite references. Future records require `institution_id NOT NULL`, tenant-first query filters/indexes, scoped uniqueness and composite foreign keys for references to tenant-owned entities. An indirect ownership path must be documented and enforced at both authorization and SQL boundaries.

**PostgreSQL row-level security is not enabled.** Current safeguards are application checks and relational constraints. Introduce RLS only with a restricted runtime role, transaction-local context, pool-leak tests, explicit worker/migration policies and cross-tenant integration tests. RLS is defense in depth and cannot replace application authorization.

Platform operators use separate role records and permission checks. Super Admin can provision an institution's new first Admin and manage its status, module entitlements and manual subscription; the platform actor receives no school membership or tenant bypass. Institution module/subscription rows have explicit institution foreign keys and tenant-first keys/indexes. Membership audit rows have composite actor/target ownership references; platform institution changes have their own attributable audit table. Support access and teaching/guardian resource relationships remain deferred. Cross-institution tenant requests return 403 without revealing existence.

Live school commands lock the institution before actor/module rows, then revalidate capability permission and resource assignment under the same transaction. Idempotency is tenant/actor/payload-scoped and does not bypass permission revalidation. School query keys include identity and institution, and the URL preserves an explicit selector when switching between assigned schools. Attendance marks/corrections, fee allocations/reversals and evidence use tenant ownership constraints; teacher access is scoped to current class assignments. See [ADR 0012](../decisions/0012-live-school-workspace.md).
