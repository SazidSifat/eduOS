# Database

PostgreSQL 18, node-postgres pooling (10 connections/process), Drizzle ORM and Drizzle Kit. Pool connections use UTC, a 3 second connection timeout and a 10 second statement timeout. Respect database URL TLS configuration; production should use verified TLS and a restricted runtime role separate from the migration role.

`schema/auth.ts` owns Better Auth user/session/account/verification/rate-limit tables. `schema/identity.ts` owns institutions, memberships, module grants and manual subscription terms. Auth IDs are UUID strings stored as text for adapter compatibility; institution IDs are PostgreSQL UUIDs. Instants use `timestamptz`; subscription period ends are calendar dates.

Constraints include unique email/token/slug/provider-account keys, membership composite PK, foreign keys, slug format and lookup/expiry indexes. Membership deletion follows user removal; institution deletion is restricted while memberships exist. Future tenant-to-tenant references must include institution ID in composite ownership constraints.

Migration `0001_institution_platform_rbac.sql` adds the five-value `institution_role` enum and nullable membership role without granting access to existing rows. A tenant/active/role index supports administrator lookups. `membership_change` records the actor, target, before/after role and active state, and UTC instant; composite foreign keys bind both memberships to the same institution. Audit references restrict deletion of their memberships, including cascaded user removal, so audited accounts should be deactivated. A production retention/erasure workflow is still required.

The separate `platform_role` enum has `platform_owner` and `platform_manager`. `platform_operator` references a global identity with role/active state; `platform_operator_change` records attributable state changes and restricts operator deletion. No platform records are seeded by migrations. Bootstrap and staff mutations share an advisory transaction lock; school membership mutations lock the owning institution row. Locks plus a last-active-administrator check enforce service-level continuity under concurrent role changes. Protected member/operator list reads hold a shared actor-row lock while querying. There is no database trigger enforcing the last-administrator rule for arbitrary direct SQL.

Migration `0002` adds nullable institution type, active/frozen/inactive access state, reason/time fields, institution-owned module grants and one optional subscription record per institution. Existing institutions remain active and unclassified; no module or subscription is fabricated. Module grants have a composite institution/module primary key and a tenant/enabled index. Subscription amounts have a nonnegative constraint and a status/period-end index. `platform_institution_change` records attributable creation, status, module and subscription changes with before/after JSON and UTC creation time. Foreign keys restrict deletion of referenced institutions/operators. API services write audit and settings atomically. First Admin identity, password hash, school membership, institution and initial module grants are also created in one transaction.

`createDatabase` returns `db`, `pool`, a transaction helper and `close`. Multi-write operations use transactions. Schema changes use `pnpm db:generate`, review SQL/snapshots, then `pnpm db:migrate`; migration execution is explicit and tracked by Drizzle, never API startup. `db:studio` requires configured reachable PostgreSQL. No automatic reset or destructive push script is provided.

Migration `0003_institution_code` adds a non-null unique six-digit institution code. The non-cycling PostgreSQL sequence allocates `100000`–`999999` and the format check rejects other values. The default backfills existing rows and also covers inserts outside the platform creation service. Codes are read-only application references; UUID ownership and authorization are preserved. Failed transactions can consume a code, and the sequence never cycles/reuses one automatically. See [ADR 0010](../decisions/0010-institution-codes.md) for deployment/backfill and capacity details.

`db:migrate` loads the API's private `apps/api/.env` when available and respects a `DATABASE_URL` already injected into the command environment. It validates the PostgreSQL URL, checks connectivity, then applies the existing migration journal. `db:migrate:check` stops after the connectivity query. Both commands close the pool and return nonzero with sanitized configuration/connection errors. Generation and Studio retain their root `.env` configuration. No schema SQL or applied migration is rewritten by this command change.

Integration tests require a dedicated `eduos_test*` database, apply committed migrations, create unique synthetic fixtures, verify authentication/isolation/rollback, and remove only their own rows. Do not point tests at development or production data. Backups, restore drills and online migration strategies need deployment-specific work before pilot use.

Migrations `0004` and `0005` add school admission candidates/settings/history/idempotency, minimal class/session offerings, durable students/enrollments, cash charges/payments/receipts and follow-up notifications. Tenant relationships use composite foreign keys and histories restrict deletion. No existing roles are changed or populated. See [ADR 0011](../decisions/0011-school-admissions.md) for write serialization, fee snapshots and explicit deployment ordering.
